## 13. 学科插件与可扩展架构：从一道题到任意题

> 目标是任意题、全学科。卡住的从来不是状态机，是**解法图需要人工标**。
> 这一章回答：怎么在不改对话内核的前提下，让解法图由模型生成、且结论仍可证伪。

### 13.1 契约早已为全学科写好

检查 `specs/` 会发现一件有利的事：产品契约本来就是按"通用认知诊断"设计的，只有一处需要改。

| 契约要素 | 现状 | 是否支持全学科 |
|---|---|---|
| `node.type` | `READ` / `CONCEPT` / `CONDITION` / `STRATEGY` / `TRANSFORM` / `COMPUTE` / `CHECK` | ✅ **认知动作，不是数学动作**——读题、概念提取、条件转译、策略选择、变形、计算、校验，换成阅读题依然成立 |
| `node.demand` | V / Gf / Gv / WM / Gs / LTS / M 七维 | ✅ CHC 七维本就跨学科 |
| `edges` | `[from, to]` 依赖对 | ✅ 学科无关 |
| `probes[].targets` | 指向节点 | ✅ 学科无关 |
| `problem.subject` | 枚举仅 `["math"]` | ❌ **唯一的契约级改动** |
| `problem.grade` | 枚举仅 `["high_school"]` | ❌ 同上 |

因此"全学科"不是推翻重来，而是**兑现一张已经写好的契约**。

### 13.2 实现层的五处硬编码

| 位置 | 现在 | 全学科要求 |
|---|---|---|
| `infrastructure/seed.py` | 一道种子题 + 4 个探针 + 标准答案 | 任意题 |
| `application/factory.py` 的 `_ALIGNMENT_SUPPORT` | 写死 `n1→H_L1` 等映射 | 每张图自己给出节点与假设的支撑关系 |
| `domain/problem/alignment.py` 的 `_NODE_RULES` | 6 条中文关键字规则 | 语义对齐（模型生成 + 校验） |
| `domain/diagnosis/hypotheses.py` 的 `EVIDENCE` | 人工写的 log-odds 表 | 按图生成证据模型 |
| `infrastructure/in_memory.py` 的 `find_for` | 关键字命中，否则 422 | 识别任意题 |

五处合起来就是一句话：**图必须人工标，所以只能做一道题。** 100 道题可以标，全学科不可能。

### 13.3 可验证性三档

卡点定位的可信度取决于该学科能否被自动验证。不分档，"有证据的卡点"会在不可验证的学科里退化成修辞。

| 档位 | 学科 | 可用验证手段 | 承诺边界 |
|---|---|---|---|
| **STRONG** | 数学 | 符号等价、数值代入、反例构造 | 定位到 L2（条件转译/参数分类），**附可证伪的反例** |
| **PARTIAL** | 物理、化学 | 量纲/单位、代数结构、数值回代 | 定位到步骤级；概念层只给"候选卡点 + 置信度" |
| **NONE** | 语文、英语、历史 | 无客观真值 | **只做结构提示**，不做卡点归因，不生成卡点卡 |

当前卡点卡之所以站得住，是因为数学能验：`ln x − ax ≤ 0` 要求对所有 `x>0` 成立，`a≤0` 这一支必须单独检查——代入 `a=−1` 看到 `f(x)→+∞`，就能证明它不满足、必须排除；学生漏的是这一步检查，不是答案里的一支。换成作文，"你卡在条件转译"无法证伪——同一句话在数学上是证据，在语文上是修辞。

分档不是降低野心，是**让野心可交付**。状态机骨架完全共用，不同的只是插件的验证器与对外承诺。

### 13.4 插件接口

放在应用层端口，实现放基础设施层，与既有 Protocol 同风格：

```python
class VerifiabilityLevel(StrEnum):
    STRONG = "strong"
    PARTIAL = "partial"
    NONE = "none"

class SubjectPlugin(Protocol):
    subject: str
    level: VerifiabilityLevel

    def identify(self, text: str) -> ProblemRef | None: ...
    def build_graph(self, problem: Problem) -> SolutionGraph: ...
    def probes_for(self, node: SolutionNode) -> tuple[Probe, ...]: ...
    def evidence_model(self, graph: SolutionGraph) -> EvidenceModel: ...
    def verify(self, step: StudentStep) -> Verdict: ...
```

三条设计约束：

1. **`verify()` 允许返回 unknown**——这是 NONE 档的诚实出口，不是缺陷；上层据 `level` 决定是否允许 `diagnose`。
2. **状态机不认识插件**——`DialogueSession`、转移表、应用服务一行不改；插件只在进入 `ALIGN` 之前提供内容。
3. **生成的图必须过 schema 校验 + 结构修复**——`solution-graph.schema.json` 已限制节点 3–20 个、类型枚举、探针 ≤10，天然是生成物的护栏。

### 13.5 生成流水线与失败路径

```text
交题 → identify() → build_graph() → schema 校验 → 关键节点抽查验证
     → probes_for() → evidence_model() → 进入现有状态机（ALIGN 起）
```

失败必须显式，不允许静默降级：

| 失败 | 处理 |
|---|---|
| 图不合法，修复 1 次仍失败 | 返回"当前版本无法拆解这道题"，**不生成卡点卡** |
| 节点 < 3 或依赖无法建立 | 同上（对应风险"约三成题目无法建图"） |
| `level == NONE` | 只出结构提示，不进入 `PROBE` |
| STRONG 档验证全部 unknown | 降级为 PARTIAL 承诺，卡点卡标注"未验证" |

### 13.6 稳定性与成本

概率生成的最大敌人是**同一道题两次生成不同的图**，会让退出条件测试不可重复。对策：`temperature=0` + 固定模型版本 + 固定 prompt 版本；生成结果按题目文本哈希缓存（`(subject, graph_id)` 已是既有索引形态）；图结构指纹写入审计日志，便于回归比对。

成本上，每题一次建图 + 探针生成，与"单次 ≤ ¥0.8"的预算需要重新核算——这是 M2 之后必须重定的一笔账。

### 13.7 实施顺序

| ID | 任务 | 验收 |
|---|---|---|
| S1 | 扩 `subject` / `grade` 枚举 | 旧用例不破 |
| S2 | 定义 `SubjectPlugin` + 可验证性等级 | 数学插件包装现有种子题，行为不变 |
| S3 | `identify()` 替代关键字匹配 | 不支持的题仍返回明确错误 |
| S4 | `build_graph()`：生成 + 校验 + 修复重试 | 20 道未见题，建图成功率 ≥80% |
| S5 | `evidence_model()` 替代硬编码证据表 | 数学诊断一致率不低于现有基线 |
| S6 | 第二个学科（物理）接入 | **全套状态机零改动**跑通 |
| S7 | NONE 档承诺降级 | 不生成卡点卡，只出结构提示 |

**S6 是架构验证的关键一步**：只有第二个学科零改动跑通，才能说"可插拔"成立。选物理而非语文，因为物理有量纲可验，能证明 PARTIAL 档有效。

> 2026-10-29 已定：S1 落地（`subject` 扩到 `math`/`physics`，`grade` 扩到三学段，均为标签、不参与路由）；S2 落地（`SubjectPlugin` + `MathPlugin` 包装种子图，行为不变，`verify()` 诚实返回 `unknown`）；S3 落地（识别从关键字匹配改为「归一化后包含已标注题原文」的严格匹配，同一知识点但不同的题返回 422，而不是拿错的图去解释）。`subject` 声明与识别结果不一致时同样返回 422。
>
> 2026-10-29 S4 落地：`build_graph()` 由 `infrastructure/llm/graph.py` 实现，流程是「模型生成 → 机械修复（重编号、删悬空边、断环、截断）→ 结构规则（无环、依赖连通、每个探针至少指向两个假设）→ `solution-graph.schema.json` → 失败重试一次」。20 道未见题结构 20/20、人工抽查 19/20（95%，门槛 80%），0 重试。抽查唯一失败是「`e^x−ax≥0` 恒成立」漏掉 `a=0` 边界——**图结构自洽不等于数学结论正确**，边界只能靠 S5 的验证器与反例兜底。另：`temperature=0` 仍不可重复（同题两次生成 7/8 个节点，图指纹不同），回归比对记录指纹，不假设两次生成一致。
>
> 2026-10-29 S5 第一阶段：证据表从全局常量改为会话数据。`HypothesisSet.from_alignment(..., evidence=...)` 接受插件给出的权重，`SessionFactory` 在创建会话时调用 `SubjectPlugin.evidence_model()`；`EVIDENCE` 只作为没有插件时的默认值。种子题补齐 `p_union` 的权重（此前该探针答了也不更新后验，白耗一轮），并加契约测试保证**每个探针的每个选项都有权重、且只指向已知假设**。10 条 golden 仍为 10/10、平均 2.40 轮，不低于基线。
>
> 2026-10-29 S5 第二阶段（生成图的证据权重）：生成图新增可选的 `probe.evidence`（`选项 → 假设 → log-odds`），生成 prompt 升级为 `graph-v2`。结构规则要求每个选项都有权重、权重键必须在该探针 `targets` 内、每个 target 至少被一个选项使用、权重有正有负（否则区分不了假设）、落在 −1~1（越界机械钳制并记录）；`MathPlugin.evidence_model()` 对生成图读取图内权重，只有已标注的种子图才回退 `EVIDENCE`，未知图返回空表而不是借用种子题的权重。真实 20 题重跑：结构 18/20（90%；`P_DERIV_007`/`P_GEOM_001` 两次生成都没有探针），**68/68 个探针、204/204 个选项都有权重，68/68 有正负对比**；4 次重试，2 次重试后通过、2 次因 `no_probes` 失败；p50 3.91s / p95 5.04s（prompt 变长使 p95 从 4.54s 上升）。**仍未解决**：`P_DERIV_003` 依旧漏掉 `a=0`——证据权重只保证「答了会更新后验」，不保证「图的数学结论正确」；后者仍要 SymPy 验证器与反例，且验证器需要图先给出可形式化的断言，属 S5 下一阶段。

### 13.8 结论

**状态机保证对话可控，学科插件保证可扩展，验证器保证诊断可证伪。**

三句话对应代码里三个可指认的位置。全学科的难点不在模型，而在**为每个学科找到"能打脸"的验证手段**——找不到的学科，就不该承诺"找到你卡住的那一步"。
