# ADR-0004: 首问 8s 预算下的生成题延迟治理

- **状态**：accepted
- **日期**：2026-10-30
- **决策者**：开发与架构评审
- **相关**：[`service.py`](../../apps/api/src/synapse/application/service.py)、[`graph.py`](../../apps/api/src/synapse/infrastructure/llm/graph.py)、[`verification/__init__.py`](../../apps/api/src/synapse/infrastructure/verification/__init__.py)

## 1. 背景

首问 P95 < 8s 是交付指标。生成图接入主链路后，未见题的首问需要现场建图，这条指标连续两轮失败：

| 轮次 | p50 | p95 | 失败形态 |
|---|---|---|---|
| run1 | 6405 ms | 9304 ms | 1 题 `bad_json`，未重试成功 |
| run2 | 6391 ms | 11856 ms | 2 题 `schema_invalid`，各重试一次 |

`scripts/eval/m2_first_question.py` 只测 `SessionService.start()`，所以这些数字是纯服务端：建图 + 对齐 + 规划 + 首问改写。

## 2. 测量（决定改哪一段）

用一次性脚本（内部测量，不随仓库发布）对真实 key 拆了四个量：

| 量 | 实测 | 结论 |
|---|---|---|
| 首 token 延迟（TTFT） | 0.8–3.0 s，随供应商波动；4 并发不排队 | 每次模型调用都有固定底价 |
| prompt 长度（prefill） | 37 tokens 与 3677 tokens 的 TTFT 无差异 | **prompt 不花钱** |
| 输出吞吐 | ≈220–320 tokens/s | **输出 token 数就是预算** |
| `import sympy` | 1665 ms | 落在第一次带 claim 的请求里 |

由此定位到三块浪费：

1. 首问还要多做一次「措辞改写」模型调用（输出 20 tokens，却要付一次完整 TTFT，实测 1.2–4.2 s）；
2. 生成图平均写 6.25 个探针、9 个节点，completion ≈1250 tokens，其中大部分是重复的 `evidence`；
3. claim 被反例推翻后重试一次，重试又要重新生成整张图（+3.5 s），外加 SymPy 的 1.7 s 首次导入。

## 3. 约束

| 约束 | 依据 |
|---|---|
| 不得为了延迟牺牲诊断能力 | 20/20 出卡率是产品基线 |
| 不得降低 0.80/0.25 的卡点门槛 | 诊断标准必须统一 |
| 生成图必须在请求内完成，不进入异步队列 | 首问体验与 8s 预算 |
| 关闭模型时，标注题行为保持不变 | 规则版是对照基线 |
| 重试、跳过、降级必须可观测 | 修复码必须进入结果 |

## 4. 选项

| 选项 | 做法 | 结论 |
|---|---|---|
| A. 给生成题单独定预算 | 标注题 8s、生成题 12s | 不选：`on:10` 灰度时学生感知不到两条预算，等于放弃指标 |
| B. 异步化/占位首问 | 先返回「正在建图」，轮询拿首问 | 不选：改产品契约，且首问体验变成两跳 |
| C. 对冲请求（hedged） | 超过 T 秒再发一份，取先到的 | 不选：成本翻倍、要处理双份合法输出，收益与 A 类改动重叠 |
| D. 换更快的模型 | 改 `deepseek-chat` 之外的型号 | 不在本次范围：ADR-0002 冻结了供应商与模型，换模型是另一份决策 |
| E. 只压输出 + 去掉装饰性调用 + 预算内重试 | 见 §5 | **采用** |

## 5. 决策

1. **生成题的首问不再改写。** `SessionService.start()` 用确定性渲染器（`GraphProbeComposer`，仍过泄漏守卫）；标注种子题的首问保留一次改写，它的措辞不是模型刚写的，而且标注路径没有建图成本。判据是 `problem.annotated`，不是学科（`service.py::_compose`）。
2. **生成图的输出预算写进 prompt。** prompt 从 `graph-v6` 起逐版收紧，现为 `graph-v9`：节点 5–7、探针 4–5（目标 5）、选项恰好 3 个、选项不超过 15 字；并要求**同一个假设在选项上既有正权重也有负权重**（只有一边的探针答了也攒不出领先差距）。实测 completion 从 ≈1250 降到 ≈900 tokens。
3. **SymPy 的导入移到组合根。** `build_container()` 对生成器调用可选的 `warm()`；`DefaultGraphVerifier.warm()` 幂等加载 SymPy。首次带 claim 的请求不再付 1.7 s。
4. **claim 重试按预算决定跑不跑。** 反例推翻答案后，只有当「已用时间 + 上一次调用耗时」仍 ≤ `graph_retry_budget_s`（默认 7.5 s）时才重试；否则保留图、丢掉 claim，并记 `retry_skipped_budget`。schema 失败的重试仍无条件——那是拿到图的唯一路径——但**重试 prompt 要求输出最小可用图（5 节点、3 探针）**，把重试成本从 ≈4.4 s 压到 ≈3.2 s。（2026-10-30 晚修订：这里改成只重写区间，不再重生成整图；见 §8。）
5. **一次模型调用只写一条审计。** claim 被推翻的「丢弃并保留图」分支原来写了两行（一行 `schema_ok=false`、一行 `schema_ok=true`），导致任何按行统计的调用数/重试数都偏高；现在丢弃的那次只写一行，最终保留的那次只写一行。

## 6. 后果

- 首问 p50 从 6.4 s 降到 **4.2–4.4 s**，p95 从 9.3–11.9 s 降到 **4.6–4.7 s**（无重试轮次）。
- 重试轮次的尾延迟 ≈4.4 + 3.2 ≈ **7.6 s**，仍在 8 s 内；p95 在 20 题里容得下最多 2 个这样的样本。
- 生成图的节点数从 ≈9 降到 ≈6、探针从 ≈6.25 降到 ≈4.9；出卡率仍 **20/20**，卡点节点 20/20 在图内（`aligned` 策略）。
- 代价一：生成题的首问是图里那条原始问句，没有二次润色。它本来就是同一个模型刚写的，这个损失目前观测不到，但不再经过首问改写器。
- 代价二：被反例推翻的 claim 在慢轮次上不再重试。此前观测到的 `P_DERIV_003` 六轮都没改对，所以预期损失接近零；换更强模型后应重新评估。
- 代价三：schema 重试拿到的是「最小可用图」（5 节点、3 探针），那一题的诊断会比正常图粗。它只影响约 5% 的会话。
- 未覆盖：真实学生作答下的出卡率。浏览器到 API 的网络与首屏渲染已在 §9 单独补测。

## 7. 验证

- 首问门禁（20 道未见题，真实 key，`on`）：run3 p50 3305 / p95 6895、run4 p50 3381 / p95 6875（`graph-v7`，3 探针）、run5 p50 4208 / p95 4690、run7 p50 4252 / p95 4619（`graph-v9`，5 探针）；run6 因两次 schema 重试 p95 8632 判 FAIL，正是 §5.4 要压的那一段。报告：`eval/reports/m2-first-question-run{3,4,5,6,7}.md`。
- 出卡率（同一 20 题，`aligned` 策略）：3 探针 15/20 → 4 探针 16/20 → 5 探针 **20/20**，卡点节点 20/20 在图内；建图 p50 4343 ms。报告：`eval/reports/m2.5-s5-session.md`。
- 物理（6 题）：建会话 6/6、出卡 6/6、节点在图内 6/6。报告：`eval/reports/m2.5-s6-physics.md`。
- 回到 `off`：`pytest` 全绿，10 条 golden 10/10，手写种子图的图与卡面不变。

## 8. 修订（2026-10-30 晚）：claim 改为只重写区间

§5.4 把「整图重生成」从 7.6 s 的尾巴压到 4.4 + 3.2 s，但重试仍然贵，而且 `P_DERIV_003` 在整图重试里六轮都没改对负参数分支。新的做法是：反例推翻 claim 后，**只发一次区间重写调用**（`purpose=graph_claim_repair`），请求里重复题目、钉死原 claim 的 `expression`/`relation`/`parameter`/`variable`/`variable_domain` 和反例，只要求返回 `{"answer":[...]}`（`max_tokens=400`）。

- **为什么钉死表达式**：否则模型可以通过改 `f(x)` 来迎合答案，反例就白给了。唯一的例外是 `verification_malformed`（表达式本身读不懂），这时允许重写整个 claim。
- **预算**：不再用「上一次调用耗时」估计，而是把这次调用的超时直接设为 `graph_retry_budget_s − 已用时间`；剩余不足 1 s 就不发，记 `retry_skipped_budget`。因此总耗时被硬性限制在预算线内。
- **结果**：`s5_verify` 的 20 题本轮建图 20/20、20 次调用、0 次重试，`P_DERIV_003` 首轮就写 `[0,e]` 并 `pass`（p50 4213 / p95 4843 ms）；本轮没有出现反例，所以另用 `scripts/eval/s5_claim_repair.py` 固定 `(-∞,e]` + 已知反例做受控探针：**3/3 修成 `[0,e]` 并通过验证**，单次 788 / 948 / 1830 ms。按建图 ≈4.5 s 计，反例样本的尾延迟从 ≈7.6 s 降到 **≈5.3–6.3 s**。
- **代价**：被推翻的 claim 只修一次，不再给第二次机会；修复失败仍是丢弃 claim、保留图。这个代价与旧版相同（旧版也只有一次）。
- **仍未覆盖**：批量里没有出现反例，所以「端到端一次真实反例」还没有样本；受控探针只证明单次调用和解析路径。此前的负参数分支问题因此从「prompt 修不好」变成「有反例就能修」，但首轮生成的正确率仍是随机变量。报告：`eval/reports/m2.5-s5-claim-repair.md`。
- **扩成五例（同日补测）**：除 `(-∞,e]` 外，又钉死了「整段漏」（`[1,e]`）、「两端开闭各错」（`(0,e]`、`[0,e)`）、「负参数段收窄」（`(-1,e]`）四种错法，各 3 次：**14/15 修对**，p50 763 ms / max 1581 ms。唯一一次失败把「偏窄」过修成「偏宽」（`[1,e]` → `(-∞,e]`），重新验证仍 `fail`；生产路径按 `claim_repair_refuted` 丢 claim、保留图，所以不会把被推翻的答案留在会话里。**修复不是单调的**，这是一次修复 + 重新验证（而不是无条件接受）的价值。

## 9. 浏览器侧端到端实测（2026-10-30 晚）

§7 的门禁只测 `SessionService.start()`，而 8 s 是对外承诺——用户感知的是「点下按钮到看见第一问」。补测在 production build 与真实 Chromium 中完成，页面内埋五个点：`submit` 事件、`fetch(POST /api/v1/sessions)` 的发出/响应头/响应体读完、`.sm-probe .sm-q` 出现（MutationObserver）、其后两帧。

| 场景 | submit→首屏 | 其中 API | 其中客户端 |
|---|---|---|---|
| 本机 loopback，未见题 n=6 | 4.26–5.63 s（p50 4.88） | 4.19–5.58 s | 56–168 ms（1.0–3.2%） |
| 4G 限速（RTT 150 ms / 1.6 Mbps），n=3 | 4.64–5.31 s | 4.16–5.07 s | 221–237 ms |
| 标注种子题（不建图） | 1.02 s | 0.95 s（一次首问改写） | 72 ms |

- **客户端那半是 1 个 RTT**：`/diagnose/[sessionId]` 是动态路由，`router.push` 之后 App Router 还要取一次 RSC payload/路由 chunk；本机 RTT≈0 时≈70 ms，模拟 4G 时≈230 ms。`submit→fetchStart` 是 0–1 ms，React 事件处理可忽略。
- **试过并否决**：在 `start()` 里 `router.prefetch("/diagnose/_")` 用建图的 4–5 s 预取下一屏。4G 下 `fetchBody→paint` 仍是 227–268 ms（不预取 221–237 ms），没有可测收益；没有 `loading.tsx` 时 prefetch 只取片段壳，实际 RSC 仍按真实 id 再取一次，只是多一个请求。已回退。
- **结论**：8 s 的瓶颈是模型输出，不是浏览器；不为这 0.07–0.23 s 改导航语义（同页渲染或加骨架屏）。这次补测排除了「前端是主要瓶颈」的可能，也补上了服务端指标的盲区。
- **限制**：单机、单浏览器、n=6/3，非 RUM；真实用户还要加 TLS 握手（首访）与设备渲染差异。要进 CI 需先给 `apps/web` 加 Playwright devDependency（当前只有 jsdom 组件测试）。
- 报告与复现步骤：`eval/reports/m2-first-question-browser.md`。
